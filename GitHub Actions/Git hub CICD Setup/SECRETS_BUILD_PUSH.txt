PART 1 — ENVIRONMENT VARIABLES
----------------------------------------------------------------

What are they?
- Key-value pairs used inside workflows.
- Used for non-sensitive config values.

Levels of env variables:
1. Workflow level  → available to all jobs
2. Job level       → available to all steps in that job
3. Step level      → available to that step only

Syntax:

    env:
      APP_NAME: my-app
      ENV_TYPE: production

Accessing in a step:

    run: echo "App is $APP_NAME"

Example — all 3 levels:

    name: Env Variable Demo
    on: [push]

    env:
      WORKFLOW_VAR: "I am workflow level"   # workflow level

    jobs:
      build:
        runs-on: ubuntu-latest

        env:
          JOB_VAR: "I am job level"         # job level

        steps:
          - name: Step with its own var
            env:
              STEP_VAR: "I am step level"   # step level
            run: |
              echo $WORKFLOW_VAR
              echo $JOB_VAR
              echo $STEP_VAR

PART 2 — SECRETS
----------------------------------------------------------------

What are secrets?
- Encrypted values stored in GitHub.
- Used for sensitive data — passwords, tokens, API keys.
- Never visible in logs (GitHub masks them automatically).

Where to add secrets in GitHub:
  Repository → Settings → Secrets and variables
  → Actions → New repository secret

Types of secrets:
1. Repository secrets    → only that repo
2. Environment secrets   → tied to a specific environment (dev/prod)
3. Organisation secrets  → shared across multiple repos

Syntax to use a secret:

    ${{ secrets.SECRET_NAME }}

Example:

    - name: Login to Docker Hub
      run: echo "${{ secrets.DOCKER_PASSWORD }}" | 
           docker login -u "${{ secrets.DOCKER_USERNAME }}" --password-stdin

IMPORTANT RULES:
- Secrets are NEVER printed in logs (GitHub masks them)
- Secrets cannot be passed between workflows directly
- Always use --password-stdin for Docker login (never plain text)

PART 3 — DOCKER BUILD & PUSH (Company Standard Way)
----------------------------------------------------------------

Why use docker/build-push-action?
- Official Docker action maintained by Docker team
- Handles build + push in one step
- Supports multi-platform builds, caching, tags

Step 1 — Store these secrets in GitHub:
  DOCKER_USERNAME   → your Docker Hub username
  DOCKER_PASSWORD   → your Docker Hub access token
                      (NOT your password — generate token
                       in Docker Hub → Account Settings
                       → Security → New Access Token)

Step 2 — Full workflow (company standard):

    name: Docker Build and Push

    on:
      push:
        branches:
          - master

    jobs:
      docker-build-push:
        runs-on: ubuntu-latest

        steps:

          # Step 1 — Checkout code
          - name: Checkout Repository
            uses: actions/checkout@v4

          # Step 2 — Login to Docker Hub
          - name: Login to Docker Hub
            uses: docker/login-action@v3
            with:
              username: ${{ secrets.DOCKER_USERNAME }}
              password: ${{ secrets.DOCKER_PASSWORD }}

          # Step 3 — Set up Docker Buildx
          # Buildx is needed for advanced builds
          # Always include this — company standard
          - name: Set up Docker Buildx
            uses: docker/setup-buildx-action@v3

          # Step 4 — Build and Push
          - name: Build and Push Docker Image
            uses: docker/build-push-action@v5
            with:
              context: .
              push: true
              tags: ${{ secrets.DOCKER_USERNAME }}/my-app:latest

PART 4 — IMAGE TAGGING STRATEGY (Company Standard)
----------------------------------------------------------------

Never use only :latest in production.
Companies always tag with something unique and traceable.

Common tagging strategies:

1. Git SHA tag — most common
   Every image is tied to exact commit that built it.

   tags: |
     ${{ secrets.DOCKER_USERNAME }}/my-app:latest
     ${{ secrets.DOCKER_USERNAME }}/my-app:${{ github.sha }}

2. Branch + SHA

   tags: |
     ${{ secrets.DOCKER_USERNAME }}/my-app:master-${{ github.sha }}

3. Semantic version (v1.0.0) — used for releases
   Based on Git tags, handled separately.

WHY THIS MATTERS IN INTERVIEWS:
If asked "how do you handle image versioning?" say:
"We tag every image with the Git SHA so any deployed image
can be traced back to the exact commit that produced it.
We never deploy :latest to production."

PART 5 — PUSHING TO AWS ECR (Company Standard)
----------------------------------------------------------------

Most companies use ECR over Docker Hub in production.
ECR = private, inside AWS, no rate limits, IAM-controlled.

Additional secrets needed:
  AWS_ACCESS_KEY_ID
  AWS_SECRET_ACCESS_KEY
  AWS_REGION             e.g. ap-south-1
  ECR_REGISTRY           e.g. 123456789.dkr.ecr.ap-south-1.amazonaws.com
  ECR_REPOSITORY         e.g. my-app

Workflow for ECR push:

    name: Build and Push to ECR

    on:
      push:
        branches:
          - master

    jobs:
      build-and-push:
        runs-on: ubuntu-latest

        steps:

          - name: Checkout Repository
            uses: actions/checkout@v4

          - name: Configure AWS Credentials
            uses: aws-actions/configure-aws-credentials@v4
            with:
              aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
              aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
              region: ${{ secrets.AWS_REGION }}

          - name: Login to Amazon ECR
            id: login-ecr
            uses: aws-actions/amazon-ecr-login@v2

          - name: Build and Push to ECR
            uses: docker/build-push-action@v5
            with:
              context: .
              push: true
              tags: |
                ${{ secrets.ECR_REGISTRY }}/${{ secrets.ECR_REPOSITORY }}:latest
                ${{ secrets.ECR_REGISTRY }}/${{ secrets.ECR_REPOSITORY }}:${{ github.sha }}

PART 6 — WHAT COMPANIES DO DIFFERENTLY TO BEGINNERS
----------------------------------------------------------------

Beginners do:                  Companies do:
---------------------------------------------------------
Hardcode image names           Use secrets + github.sha tags
Use :latest only               Tag with SHA + semantic version
One big workflow file          Split CI and CD into separate files
Push on every commit           PR approval required before merge
Static AWS keys in secrets     OIDC (no static keys at all)
No build caching               Cache Docker layers to speed builds
No scan before push            Run Trivy/Snyk scan before push
